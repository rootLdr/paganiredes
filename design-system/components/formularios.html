Formulários

Os campos são a conversa entre a Pagani e quem pede um orçamento. Devem ser claros, cordiais e sem pressa: rótulo sempre visível, altura confortável de toque (44px) e mensagens que ajudam em vez de cobrar. Nada de urgência artificial — só o pedido de informações necessárias para dar um bom retorno.

Campo de texto

A base de todo formulário. Um rótulo acima (nunca só placeholder), o campo com 44px de altura e uma dica opcional logo abaixo para orientar o preenchimento.

Usamos seu nome apenas no retorno do orçamento.

Quando usar
  • Dados curtos e diretos: nome, cidade, bairro.
  • Sempre com rótulo visível e, quando útil, uma dica curta.
  • Marque o obrigatório com o asterisco * no rótulo.
Quando evitar
  • Para textos longos — prefira o textarea.
  • Não substitua o rótulo pelo placeholder (ele some ao digitar).
  • Não peça dados que você não vai usar no retorno.

Acessibilidade: label ligado ao campo por for/id; a dica é anunciada por aria-describedby.

Telefone e e-mail

Campos de contato com o tipo correto (tel e email), o que abre o teclado adequado no celular e ativa a validação nativa do navegador.

Com DDD. É por aqui que retornamos o contato.

Opcional — usamos só se você preferir e-mail.

Quando usar
  • type="tel" para telefone e type="email" para e-mail.
  • Placeholder mostra o formato esperado, sem substituir o rótulo.
  • Deixe claro qual canal é o principal de retorno.
Quando evitar
  • Não force máscara rígida que rejeite números válidos.
  • Não exija e-mail se o WhatsApp já basta para o retorno.
  • Evite pedir telefone fixo e celular em campos separados.

Acessibilidade: o tipo semântico do input orienta leitores de tela e o teclado móvel; dica ligada por aria-describedby.

Seleção (select)

Para escolher um item de uma lista fechada e conhecida — como o serviço desejado. Mantém o formulário curto quando as opções são poucas e estáveis.

Não sabe qual? Escolha o mais próximo — ajustamos no contato.

Quando usar
  • Lista curta e estável (até ~7 opções conhecidas).
  • Uma única escolha por vez.
  • Sempre com uma opção-guia inicial ("Selecione um serviço").
Quando evitar
  • Duas ou três opções — use radios, mais visíveis.
  • Seleção múltipla — use checkboxes.
  • Listas enormes que pedem busca.

Acessibilidade: rótulo associado por for/id; a seta é decorativa (CSS), o controle continua nativo e navegável por teclado.

Área de texto (textarea)

Para mensagens livres — descrever o local, medidas aproximadas ou dúvidas. Redimensionável na vertical, com altura mínima confortável.

Quanto mais detalhes, mais preciso fica o orçamento.

Quando usar
  • Respostas abertas e de tamanho variável.
  • Contexto que ajuda o orçamento (medidas, andar, uso).
Quando evitar
  • Dados estruturados (telefone, e-mail) — use campos próprios.
  • Como campo obrigatório longo que trava o envio.

Acessibilidade: rótulo associado; a dica descreve a expectativa sem obrigar. Redimensionamento apenas vertical evita quebrar o layout.

Escolhas: caixa e opção (checkbox e radio)

Radios para uma escolha única entre poucas alternativas; checkboxes para consentimentos e seleções múltiplas. Cada opção é um alvo generoso, com o texto clicável junto do controle.

Quando usar
  • Radio: escolha única entre 2 e 5 opções visíveis.
  • Checkbox: consentimento explícito ou várias seleções.
  • Agrupe radios com fieldset/legend.
Quando evitar
  • Radio para muitas opções — prefira o select.
  • Consentimento pré-marcado — deve ser ação do usuário.
  • Texto minúsculo fora do alvo de clique.

Acessibilidade: o label envolve o controle e o texto, ampliando o alvo; radios compartilham o mesmo name; grupo descrito por legend.

Envio de imagem (upload)

Uma foto do local costuma valer mais que muitas palavras. O campo é opcional e aceita arrastar-e-soltar ou clique para abrir o seletor de arquivos.

Quando usar
  • Quando uma imagem acelera o entendimento do serviço.
  • Sempre como opcional, para não travar o envio.
  • Deixe claros formatos e tamanho aceitos.
Quando evitar
  • Como etapa obrigatória do orçamento.
  • Sem indicar limite de tamanho ou formato.
  • Para documentos sensíveis não pedidos.

Acessibilidade: a área visível é um label ligado a um input type="file" real (visualmente oculto, mas focável), mantendo teclado e leitores de tela funcionais.

Estados de validação

A mensagem aparece perto do campo, é específica e diz o que fazer. Erro em vermelho, sucesso em verde — e sempre com texto, nunca só cor. Campos indisponíveis ficam desativados de forma legível.

Campo desativado: preenchido automaticamente.

Quando usar
  • Valide após o preenchimento, não a cada tecla.
  • Mensagem específica e próxima do campo em questão.
  • disabled apenas para valores que o usuário não altera.
Quando evitar
  • Mensagens genéricas ("campo inválido").
  • Sinalizar só por cor, sem texto ou ícone.
  • Bloquear o envio sem explicar o porquê.

Acessibilidade: o campo em erro usa aria-invalid e liga a mensagem por aria-describedby; a distinção não depende apenas da cor (ícone + texto).
